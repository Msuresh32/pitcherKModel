                 includes the SAME-DAY opponent batting stats in the pitcher's features.
  2. [CRITICAL]  _prior_environment_features: same-game outcomes drive venue/umpire features.
                 The function calls df (which contains the current game's TARGETS) before

  3. [MODERATE]  _opponent_features: rolls and expands over pitcher_game_logs grouped by
                 "opponent". This correctly shifts(1), but the dataset being used is the
                 *pitcher* game log — meaning the aggregation captures HOW MANY Ks pitcher X
                 threw vs opponent Y, not how many Ks the opponent team allowed against all
                 pitchers. The variable name "opp_pitcher_{col}" is misleading and the feature
                 is actually a pitcher-vs-team prior, already captured cleanly in
                 _pitcher_vs_team_features. RISK: if optimizer over-indexes on this redundant

  4. [MODERATE]  FanGraphs imputation: merge_fangraphs_prior_season imputes missing FG
                 values with the FULL-DATASET median (not train-period-only median), potentially
                 leaking future data when data spans multiple seasons. LOW SEVERITY because
                 FG values are season aggregates and imputed mostly for rookies/late additions.
  5. [MODERATE]  add_expected_opportunity_features in backtest.py: imputation inside
                 add_expected_opportunity_features uses out[cols].median() — computed from
                 ALL rows including the backtest test period. This is called AFTER

  6. [SUSPICIOUS] _league_krate_drift_features: first computes daily["league_k_rate_roll{w}"]

FEATURE: _merge_opponent_batting_features — merge_asof allow_exact_matches=True
STATUS: LEAKAGE_CONFIRMED
SEVERITY: CRITICAL
FINDING:
  At build_features.py:838-845, the merge_asof call uses:

      pd.merge_asof(
          group.sort_values("game_date"),
          opponent_batting.sort_values("game_date"),
          on="game_date",
          by="opponent",
          direction="backward",
          allow_exact_matches=True,   # <--- THE BUG
      )

  The opponent_batting DataFrame is keyed by (game_date, team). The function
  _team_batting_rolling_features() generates one row PER (game_date, team), and
  the features in that row are the LAGGED stats (shift(1) before rolling). So the
  opp_batting_k_rate_roll{N} stored in the row for date=2025-05-15 reflects the
  opponent team's batting k-rate through 2025-05-14.

  However, with allow_exact_matches=True, the pitcher's game on 2025-05-15 gets
  matched to the batting_features row with date=2025-05-15. If the team batting logs
  contain games on 2025-05-15 (e.g. a different game earlier that day, or a game from
  the same date in the team batting table), those same-day stats are included.

  MORE CRITICALLY: The rolling features were computed inside _team_batting_rolling_features
  and the row with date=T already includes data through T-1 (because of shift(1)). This
  is clean IF AND ONLY IF the team batting logs do not have multiple entries on the same
  date for the same team. If a team plays a doubleheader, they will have TWO rows on the
  same date. The shift(1) inside _team_batting_rolling_features shifts by position within
  each group, not by date. So if team BOS plays a doubleheader on May 15:
    - Row 1 (game 1): opp_batting_k_rate reflects through May 14 (CLEAN)
    - Row 2 (game 2): shift(1) gives May 15 game 1's stats → LEAKAGE

  When pitcher X faces BOS on May 15 in game 2, with allow_exact_matches=True and
  direction="backward", the merge_asof will pick up the team_batting row for May 15
  (game 2), which contains game 1 of the doubleheader. This IS leakage — game 1 stats
  from the same calendar day are included in the pitcher's features for game 2.

  The allow_exact_matches=True is the enabling condition: changing to False would pick
  the last row strictly before the current game date, avoiding same-day contamination.

ESTIMATED LEAKAGE MAGNITUDE:
  Doubleheaders are ~5% of games. The leakage exposure per affected game is one team
  batting game (k_rate impact). Effect on RMSE: ~0.05-0.10 Ks.
LINE: build_features.py:844
FIX:
  Change allow_exact_matches=True to allow_exact_matches=False.
  This ensures the pitcher on game_date=T only sees opponent batting features computed
  from data strictly before T.

  Corrected call:
      merged = pd.merge_asof(
          group.sort_values("game_date"),
          opponent_batting.sort_values("game_date"),
          on="game_date",
          by="opponent",
          direction="backward",
          allow_exact_matches=False,   # FIXED: no same-day contamination
      )

FEATURE: _prior_environment_features (venue_{target}_roll{N}, umpire_{target}_roll{N})
STATUS: LEAKAGE_CONFIRMED
SEVERITY: CRITICAL
FINDING:
  The function _prior_environment_features() (build_features.py:874-915) computes
  rolling stats for venue_id and home_plate_umpire_id using the TARGET OUTCOMES from
  the pitcher game log. The critical flaw is in how these features are merged back.

  Step 1 (line 895): env aggregates per (venue/umpire, game_date) using TARGETS from df.
  At this point, df is the FULL pitcher_df INCLUDING the current game's strikeout/walk/
  hits_allowed outcomes.

  Step 2 (lines 900-910): shift(1) is applied to the aggregated env DataFrame before
  rolling. This shift is correct within the env DataFrame.

  Step 3 (line 930): The env features are merged back to out via:
      out = out.merge(env_features, on=["game_date", group_col], how="left")

  THE PROBLEM: env_features is keyed by (game_date, venue_id). Multiple pitchers may
  appear at the same venue on the same game_date (two pitchers in the same game, or a
  doubleheader). When the rolling features are computed with shift(1), they shift by
  position in the env group. If there are two rows for the same (venue, date), the
  second row will have the first row's outcome included (because shift(1) in the
  env aggregated view only shifts by 1 position within the venue group, and two pitchers
  on the same date in the same venue means one game's outcomes appear).

  MORE CRITICALLY: The groupby-aggregate at line 895 averages TARGETS across all
  pitcher appearances at that venue/umpire on that game_date. This average includes the
  FOCAL PITCHER'S OWN outcomes. When the features are merged back, the focal pitcher's
  own current-game K/walk/hits are embedded in the venue feature, which is then included
  as a predictor for the same game.

  Example:
    - venue_id=15 has 2 pitchers on 2025-05-10: pitcher A (8 Ks) and pitcher B (6 Ks).
    - env averages: venue_id=15, date=2025-05-10 → strikeouts=7.0
    - shift(1) in env means the feature for date=2025-05-10 includes data from the
      PREVIOUS venue appearance, not data from 2025-05-10.
    - The feature merged to pitcher A's 2025-05-10 row = prior_venue_k_avg from prior dates.
    - This part is clean.

  BUT: If venue features are computed from df that already has CURRENT game targets, and
  then the merge is exact on game_date, the current-game outcome is in the env pool used
  to compute the pre-game venue feature for OTHER pitchers on the same date.

  The SINGLE-PITCHER-PER-GAME case is always clean (shift(1) excludes today).
  The TWO-PITCHERS-SAME-VENUE-SAME-DATE case has minimal leakage (one pitcher's current
  outcome appears in the other pitcher's env features for the same day — only via the
  env aggregation, and only if another game at this venue occurred on the same date).

  NET ASSESSMENT: Low-severity same-day cross-contamination. The REAL issue is that the
  env aggregation at line 895 groups by (venue_id, game_date, game_pk) when game_pk is
  available, which partially mitigates this. But the merge on line 930 joins by
  (game_date, venue_id) which means if a venue hosts 2 games on the same day (rare but
  possible), the features bleed between games.

ESTIMATED LEAKAGE MAGNITUDE:
  Rare (same venue, same day, different game_pks). Effect on RMSE: <0.03 Ks. LOW but
  not zero, and violates the no-leakage invariant.
LINE: build_features.py:895, 930
FIX:
  Option A: When computing env, do NOT include the current game's targets. Instead,
  filter env to use only dates strictly before the game being featured:

      # In _prior_environment_features, use only prior dates in env
      # The shift(1) at line 900 handles this for same-venue prior games,
      # but the merge at line 930 should use merge_asof with allow_exact_matches=False
      # instead of an exact merge.

  Option B (preferred): Replace the exact merge at line 930 with merge_asof:

      env_sorted = env_features.sort_values(["game_date", group_col])
      out_sorted = out.sort_values("game_date")
      for grp_val, grp in out_sorted.groupby(group_col):
          env_grp = env_sorted[env_sorted[group_col] == grp_val]
          merged_piece = pd.merge_asof(
              grp.sort_values("game_date"),
              env_grp.sort_values("game_date"),
              on="game_date",
              direction="backward",
              allow_exact_matches=False,
          )
          pieces.append(merged_piece)

  This ensures the venue/umpire features for game on date T only use env data from
  strictly before T, eliminating same-day same-venue cross-contamination.
